## 直したら必ず push する

**ローカルでコミットしてデプロイしただけでは、次の自動更新に消される。**
毎日の更新は GitHub のリポジトリからコードを取り出して動くので、push していない
変更は「無かったこと」として本番が作り直される。2026-08-29 にこれが起きて、
タブ・全機種シート・未実施の改修がまとめて巻き戻った（24コミットが未pushだった）。

    cd /Users/Shared/kabaneri-counter/github-pages
    git add -A && git commit -m "..." && git push origin main
    npx wrangler pages deploy . --project-name=kabaneri-counter --branch=main

自動更新が先に走っていると push が弾かれる。そのときは `git fetch` してから
`git merge origin/main` し、`toho/data/events.json` の衝突は生成物なので
`git checkout --ours` で自分側を採用し、`events.py` と `src/build-pages.py` を
流し直してからコミットする。


## 分析するときに忘れないこと

**バラも全系に含める（2026-08-28にユーザー確認済み）。**
記事タイトルは「全系6機種+バラ3機種」のように分けて書かれ、結果欄（台数つき）に
載るのが「全系」、連想の見出しにだけ出るのが「バラ」。全体の15.7%（189件）が後者で、
その68%が1台構成。**これらも全系として数えるのが正しい。**
結果欄だけに絞ろうとしないこと。


**結果欄には全台系でないものが混ざる。色付きは機種イベントの一覧表。**
「かぐや様（ピンク）」「モンキーV（青）」のような色付きの行は、4のつく日の
機種イベント対象台を示す一覧であって、その日の全台系ではない。
6/04・6/14・7/04の3日にこれが載っており、括弧書きを外す処理を入れたときに
全台系として数えてしまっていた（2026-08-28にユーザーが発見）。
`events.py` の `COLOR_TAG` で除外している。台数としては使う。
**タイトルに「◯機種が全系に！」と書いてあるので、件数が合うかで検算できる。**


**単独の軸だけ見ると傾向を見逃す。掛け合わせを見ること。**
小台数（4〜9台）のジャグラーがその実例。3のつく日で
- ジャグラー系統だけ見ると 8/12回（全体74%）で**平均以下**
- 小台数だけ見ると 11/12回（全体94%）で**差なし**
- 掛け合わせると 8/12回（全体54%）で **+13**
どちらの軸も「当たり前に来るもの」なので単独では埋もれる。
島として意味のあるまとまり（ジャグラーコーナーの5台6台、など）は
軸を分解すると消えてしまう。

**小台数ジャグラーは実在する強い傾向なので、今後も必ず見ること。**
現在の出方: 7のつく日 10/12回、22日・24日・27日 6/7回、あかまる取材 4/5回、
3のつく日・5のつく日 8/12回、月末最終日 4/6回。
`events.py` の `smalljug_share()` で集計、`src/events.html` の系統行に表示。

未実施: 系統×台数帯の総当たり（小台数のハナハナ、多台数のジャグラーなど）で
ほかに見落としがないか洗う。


**開催回数が少ない日は「100%」に意味がない。必ず全体と比べること。**
ママ誕生日（6回）で「小台数4〜9台と3台以下がどちらも6/6回＝毎回入っている」を
特徴として書いてしまったが、全体でも94%・90%あり、6回続くのは7割方起きる。
ユーザーに指摘されて撤回した（2026-08-28）。
差を見ずに割合だけ見ると、当たり前のことを傾向として書いてしまう。

### H. INPの5.7秒は実測で棄却。再点検は2026-09-05以降
Cloudflare の Debug View に `#tabs>button` **5,704ms が3件**あり、申し送りでは
「smoothスクロールが犯人」「データ到着前のタップで例外」と見立てられていた。
**2026-08-29に本番で実測したところ、どちらも当たらなかった。**

| 測ったもの | 結果 |
|---|---|
| タブを実際にクリック→画面が変わるまで | **24ms**（処理2ms＋描画22ms） |
| 検索窓に1文字（最も重い「あ」＝25件表示） | 14.9ms（低速端末8倍換算でも約119ms） |
| 読み込み時の正規化（1,528件） | 3.4ms |
| カード12枚の描画 | 0.5ms |

**24msはページ下部から押して smooth スクロールが走っている最中の値。**
INPは「次に画面が描き変わるまで」を測るもので、スクロールのアニメーション終了は
待たない。つまり smooth スクロールはINPを伸ばしていない。
データ到着前のタップも、再現したところ**タブの光りは移り、届いた時点で
正しく描き直される**（自分で治る作りだった）。

処理が2msなので、5.7秒はコードの遅さでは説明がつかない（50倍足りない）。
数千回のうち3件という出方と桁から、**タップ直後に画面が裏に回った**
（ホームに戻る・アプリ切り替え・画面ロック）ケースの可能性が高い。
このときINPは「戻ってきたときの描画」までを数えるので数秒になる。断定はできない。

**やったこと：** `render()` の先頭に `if(!DB){ tabCounts([], false); return; }` を1行。
読み込み前に押しても例外が出ず、タブの見た目だけは先に動く。
これでINPの数字は動かない見込み（原因ではないため）。

**再点検：2026-09-05以降。** 件数が増えても `#tabs>button` の異常値が残るなら、
そのとき端末とネットワークの条件込みで追う。減っていれば閉じてよい。
**動いているものを、原因が分からないまま最適化しないこと。**

## 済んだこと（2026-08-29）

- **「今日／明日の傾向」カードをトップに置いた**（申し送りの1件目・導線）。
  初日実測で `/matsuwaru/toho/` 2,131人のうち `/events` 到達が **210人＝9.9%** だった件への対策。
  検索結果の上に、その日のイベントの傾向を出すカードを置いた。
  - **構成**：肩書き（今日/明日の傾向）＋日付・イベント名 ／ 傾向文 ／ 金銀銅の上位3機種 ／
    「続きを読む・系統・台数帯・過去の全系◯機種」。カード全体がリンク。
  - **傾向文**は手書きがある9件（d6 d7 d8 d9 w22 w26 s1 s2 s11）はその文、
    残り14件は実績から自動生成（「大都が13/14回。中台数が軸」の形）。
    自動生成の条件は**全体との差が8ポイント以上**、かつ系統は**その日の半分以上で起きていること**。
    半分の条件が無いと「ディ・ライトが3/12回」のような、狙い目にならない文が出る。
  - **右上のバツで消せる**。消えるのは**その日ぶんだけ**で、日が変われば また出る
    （中身が毎日変わるため。2026-08-31にユーザーと合意）。端末内にだけ残り、送信はしない。
    骨組みごと出さないよう、`<main>` の中の小さなインラインscriptで先に判定している。
  - **データは `data/lead.json`**（5KB）。events.json は71KBあり検索ページの初期表示に乗せたくないので、
    カードに要るぶんだけ `events.py` が別に書き出す。sw.js のキャッシュ対象にも追加済み。
  - **「今日」と「明日」は20:30で切り替わる**（店長ポストの時刻。イベント傾向ページと同じ判定）。
  - **日付が重なる日の優先順位を直した**。6/30 は「0のつく日」と「月末最終日」の両方に当てはまるが、
    集計では月末最終日を採っている。カードと**イベント傾向ページの両方**を、
    日付ぴったりのイベント（21-27WEEK・月末最終日）が◯のつく日より優先されるよう揃えた。
  - 骨組みを実物と同じ高さ(340px)にしてあるので、**CLSは増えていない**（実測で見える範囲のずれ0）。
  - **効果の測り方**：他を触っていないので、翌日の `/events` ÷ `/matsuwaru/toho/` がそのまま成績になる。
    **9.9% → 25〜30%が目標。届かなければ原因は導線ではなく中身の魅力**と分かる。

- **読み込み中の骨組みを置き、レイアウトのずれ（CLS）を潰した。**
  Cloudflare で CLS が Poor 19%。本番実測（iPhone幅375）で、フッターが読み込み直後の

  結果一覧は画面の上端より下から始まるので、**100vh 取れば後ろの中身は端末を問わず
